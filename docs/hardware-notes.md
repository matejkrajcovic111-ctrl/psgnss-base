# Hardware notes

Things about this hardware that are not in a datasheet, or are and are wrong.
All of them were measured on a running station, several of them after they had
already cost a day.

## The receiver

**It cannot emit RTCM ephemeris.** The u-blox ZED-X20P's configuration key set
has no 1019, 1020, 1042, 1045 or 1046 — checked against the full 800-key
`CFG-MSGOUT` dump, not inferred. PSGNSS synthesises them from `RXM-SFRBX`
instead. If you want navigation messages on a mountpoint, that is where they
come from.

**GLONASS is not supported by this firmware.** `MON-VER` reports
`GPS;GAL;BDS / SBAS;QZSS / NAVIC`. 1084 and 1087 can be enabled on USB and emit
nothing. Do not try to "fix" it, and do not advertise GLONASS in a mountpoint's
`nav_system` — promising a constellation the stream does not carry is worse
than not offering it.

**It emits MSM4 and MSM7 concurrently**, which is why a mountpoint can be a
pure filter and nothing is ever transcoded.

**It emits 1005 and never 1006, 1008 or 1033.** Those three are generated by
PSGNSS from configuration.

**`CFG-SIGNAL` writes reset the GNSS subsystem.** u-blox says to wait for the
ACK and then 0.5 s before the next command. PSGNSS waits a full second after
any batch touching that group and retries the read-back. Measured on a live
enable-and-revert: epoch age stayed 0–1 s and the hub dropped nothing.

**`VALSET` takes at most 64 keys.** Larger transactions are chunked on write,
persist and revert.

**`UBX-MON-SYS` `tempValue` is documented as unsupported** on HPG 2.00 and
always reads 0, so no receiver temperature is shown. `errorCount` climbs
steadily on a healthy receiver; nothing is known about what it counts.

**RAM and Flash configuration are byte-identical** once committed, so the
configuration survives a power cycle.

## Reference station ID

The generated 1006/1008/1033 and the receiver's own 1077/1097/1127 **must carry
the same reference station ID**. When they disagree, a rover receives a
healthy-looking stream, tracks satellites and **never fixes** — it cannot
associate the observations with a base position.

This receiver family stamps `DF003 = 0` out of the box, so 0 is the answer
unless you are also writing `CFG-RTCM` on the receiver. Change one without the
other and the symptom is a station that looks perfect and serves nothing
usable.

## Epoch termination

The receiver marks the end of each epoch once, on the last message it emits. A
mountpoint serving a subset of messages filters that marker away, and the rover
then cannot close the epoch until the next one starts — one full second of
extra correction age, invisible except as worse performance. Each mountpoint
marks its own last observation message instead.

## RINEX conversion (`convbin`)

**`-f` must be 4 on this receiver.** Measured:

| `-f` | Result |
|---|---|
| 2 | GPS L1/L2 and Galileo E1 only. **BeiDou absent entirely.** |
| 3 | Adds GPS L5, Galileo E5a, BeiDou B2a |
| 4 | Adds Galileo E6 and BeiDou B3I — complete |
| 5+ | Identical to 4 |

A tool that hardcodes 2 — an F9P-era default — silently produces RINEX with no
BeiDou at all. PSGNSS refuses to start if the configured count would lose
signals the receiver tracks.

**BeiDou B1C never appears in RINEX at any setting.** That is an RTKLIB mapping
limitation, not a configuration mistake.

**`-ts` and `-te` take the date and the time as two arguments.** Passing
`"2026/09/14 09:00:00"` as one makes convbin swallow the next flag and silently
convert the whole file. This is invisible if you only ever request whole days.

**convbin makes an unpredictable number of passes** over a file and reports
progress as a timestamp on stderr. PSGNSS computes progress monotonically,
because a bar that jumps backwards is worse than one that stalls.

**Version:** `convbin --version` prints its banner; with no arguments it prints
only "no input file". `psgnssd --dependencies` reports what is installed.

## RINEX navigation data

RTCM carries observations and no navigation data, so a RINEX file converted
from an RTCM-only archive has a `.obs` and no `.nav`. The navigation archive
records `RXM-SFRBX` **and** `RXM-RAWX`: the subframes carry the broadcast
ephemeris, and the raw measurement epochs carry the receiver time RTKLIB needs
to date them. An SFRBX-only file looks valid and cannot be converted.

## systemd

**`ProtectSystem=strict` blocks writes to the archive mount** unless its path is
in `ReadWritePaths`. Without it, every write to a perfectly healthy, read-write
share fails with "read-only file system" — and the only symptom is an empty
archive and a line in the log. This cost a full day of recording once.

**A mount unit's filename must be the systemd-escaped mount path.**
`/mnt/gnssraw` must be `mnt-gnssraw.mount`. Any other name and the unit is
inert: it is never read, the share is never mounted, and nothing complains.
`psgnssd --setup` derives the name with the same rules systemd uses and the
tests check it against `systemd-escape` itself.

## Operational

**Filenames are generated in UTC.** Formatting them in local time produces an
hour that shifts twice a year and breaks continuity with everything already
recorded.

**Shutdown is not file completion.** Treating a stop as the end of a file
discards the spool copy and the resume state, fragmenting the day on every
restart.

**A long `ssh` command that hits a local timeout leaves the remote process
running.** This has caused a phantom "performance regression" more than once —
an orphaned helper spinning at 81% of a core for the best part of an hour.
Before calling anything done, check what is actually running on the station.

**`psgnssd` uses about 0.35% of one core.** If the machine looks busy, it is
something else.
